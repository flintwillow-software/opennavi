# 0045 — What a grown module graph costs the build: the go directive and the CI workspace

## Context

[ADR 0041](./0041-go-libp2p-as-the-peer-transport-dependency.md) measured what
adding `go-libp2p` costs and named three consequences: **+122 modules**, a
**~+29.5 MB binary**, and **routine `go.sum` churn**. It also asserted:

> **The templates' `go.mod` files are unaffected** until a template imports the
> host; the nested modules pick the dependency up through their own `require`
> when they do.

That sentence is true of the *templates* and was the whole of the record's
attention to nested modules. Implementing the dependency (NAVI-629 piece 3,
[ADR 0044](./0044-the-peer-host-declaration.md)) showed the record **understated
and mis-scoped** the build-side cost. Three things happened that the record did
not predict, and the third failed CI in six seconds:

1. **The root `go.mod` directive moved `go 1.26` → `go 1.26.0`.** Once the
   pruned module graph records the libp2p closure, the two-component directive
   is not enough: `go build ./...` under `-mod=readonly` (Go's default) fails
   with `updates to go.mod needed; to update it: go mod tidy`. The
   patch-version form is what records the pruned graph, and `go mod tidy`
   writes it.

2. **The out-of-repo testdata modules needed the same bump, and one needed the
   closure.** `internal/testdata/{external-component,external-backend,external-navi}`
   each carry a `replace` to the root, so growing the root's graph changes
   their resolution. `external-navi` (the only one that imports `navi/`) gained
   the full libp2p closure in `go.mod`/`go.sum` (~225 `go.sum` lines); the other
   two needed only the directive bump. ADR 0041 named the *templates* and missed
   the *testdata* modules entirely — they are the out-of-repo consumers the
   `external modules` CI job actually builds, and they are not in `go.work`.

3. **The CI-only `go.work` version is hand-written and can drift from the root's
   directive.** `.github/workflows/ci.yml` generates a `go.work` for the
   templates job that said `go 1.26`. With the root now at `go 1.26.0`, that is
   *lower* than the root requires, so **every template build failed** with
   `module ../.. requires go >= 1.26.0, but go.work lists go 1.26`. The file is
   generated by a heredoc in the workflow, not by `go work use`, so nothing
   keeps its version in step with the root.

There is also a **diagnostic trap** worth recording, because it cost a failed CI
run: the local toolchain is Go 1.27, under which the root builds fine at
`go 1.26`. CI pins **Go 1.26** (`setup-go: go-version: '1.26'`), under which it
does not. A local green build is not evidence about this class of change.

## Decision

1. **The go directive is part of the dependency cost, and moves with the module
   graph.** When the root's `go.mod` directive must change to record a grown
   graph, that change ships **in the same PR as the dependency** — not as a
   follow-up — because the two are one atomic fact: the module graph the
   directive describes is the graph the dependency created. The root is at
   `go 1.26.0` and stays there until the graph says otherwise.

2. **Every out-of-repo module in `internal/testdata/` is refreshed in the same
   PR.** They are consumers with a `replace` to the root, so a root graph change
   is their graph change. A module that imports the root compositionally
   (`external-navi`) carries the closure in `go.mod`/`go.sum`; a module that
   imports only contract packages takes the directive bump alone. The PR that
   grows the graph verifies all three under `GOWORK=off` (their CI condition).

3. **The CI workspace version must equal the root's directive, and the workflow
   is where that is enforced.** The templates job's generated `go.work` says
   `go 1.26.0`, matching the root. A generated workspace that lags the root is
   not a warning: it fails every build inside it, so the two are checked
   together.

4. **The verification for this class of change is `GOTOOLCHAIN=go1.26.0
   GOWORK=off GOFLAGS=-mod=readonly go build ./...`, not the local toolchain.**
   The `external modules` job has always run with `GOWORK=off`; this record makes
   explicit that a *local* `go build` under a newer toolchain proves nothing
   about it, and that the peer-dependency PR is verified the way CI runs.

5. **This is a consequence of ADR 0041, not a new trade.** The dependency is
   still accepted on ADR 0041's terms; what changes is the record of what the
   acceptance costs the build. ADR 0041's "templates' `go.mod` files are
   unaffected" stands for the templates and is corrected for the testdata
   modules by this record.

## Consequences

- **A dependency bump is now a four-file class of change**: `go.mod`, `go.sum`,
  the testdata modules' `go.mod`/`go.sum`, and — if the directive moves — the CI
  workflow's `go.work` heredoc. A reviewer reads the directive and the module
  count, not the hash diff (ADR 0041's own advice).
- **The go directive is a reviewable number.** A PR that moves it is a PR that
  changed the module graph, which is a fact worth seeing in the diff rather than
  discovering in CI.
- **The CI workspace is a maintained artifact, not an incidental one.** It was
  already generated by a heredoc; this record makes its version a thing that must
  track the root rather than a thing that happened to be right.
- **The toolchain-pinning trap is named.** A local build under Go 1.27 at
  `go 1.26` is not evidence; the verification command above is.
- **No new dependency and no new package.** This is bookkeeping ADR 0041's
  decision already implied.

## Alternatives considered

- **Keep the root at `go 1.26` and avoid the bump.** Rejected: it builds under
  Go 1.27 but fails `-mod=readonly` under Go 1.26 (CI's toolchain), which is the
  toolchain that decides.
- **Ship the go.mod/testdata refresh as a follow-up PR.** Rejected: it would
  leave `main` red between the two, and the directive describes the graph the
  same PR created.
- **Stop pinning the CI toolchain and let it float.** Rejected: the pin is
  deliberate (the module's `go` line and the CI Go version are one contract), and
  floating it would hide exactly the failure this record is about.
- **Generate the CI `go.work` with `go work use` instead of a heredoc.**
  Considered, not adopted: `go work use` in CI would still need the `replace`
  directive the heredoc supplies, and the heredoc keeps the CI workspace explicit
  and reviewable. Recorded as an open question rather than a decision.
- **Add the testdata modules to the committed `go.work`.** Rejected: the
  `external modules` job's whole point is to build them as a downstream consumer
  does — with their own `go.mod`, no workspace — so putting them in the workspace
  would test the wrong thing.

## Open questions

1. **Whether the CI `go.work` should be generated rather than heredoc'd**, so its
   version cannot drift from the root. A script that reads the root's directive
   and emits the workspace would remove the failure mode; it is deferred because
   the heredoc is currently explicit and reviewable.
2. **Whether the `go` directive bump deserves a CI check** — a job that fails
   when the root directive and the CI workspace version disagree, rather than
   letting the templates job discover it.
