### Added
- Forgejo connector (NAVI-413, ADR 0014/0020): `connector/forgejo` lets a navi act in a self-hosted Forgejo instance — the second forge connector, and the test of whether the connector seam generalizes across forges rather than being GitHub-shaped. It is native Go over the **Gitea-compatible REST API** (`<instance>/api/v1`), so each capability is an ordinary `tool.Tool` built with `connector.SendTool` and added explicitly, never auto-registered. Nine egress tools ship: `forgejo_issue_list`, `forgejo_issue_get`, `forgejo_issue_create`, `forgejo_issue_update`, `forgejo_issue_comment`, `forgejo_pull_list`, `forgejo_pull_create`, `forgejo_repo_get`, and `forgejo_label_list` — reads are read-only, writes execute-level. The credential is an access-token **reference** (ADR 0008), read at the call site and never stored, and the instance root is a compiled endpoint default (`DefaultBaseURL`, overridable at runtime) following the `github.DefaultBaseURL` pattern. An unset credential disables the capability, not the navi (ADR 0020 decision 7): `Start` warns once naming the reference and each egress call refuses. Three Forgejo/GitHub divergences are handled rather than papered over: **labels are assigned by id**, so a label name is resolved against the repository's label list first (an unknown name is refused, never silently dropped); **pull requests share the issues endpoint**, so a list filters `type=issues` while the pull tools use `/pulls`; and **pagination is reported in the `X-Total-Count` header** rather than a response envelope, so a list returns `count` and `total` and accepts `page`. The auth header uses the documented `token` scheme rather than `Bearer`. An opt-in live smoke test (`FORGEJO_LIVE_SMOKE=1`, skipped by default) creates, comments on, updates, reads back, and deletes a scratch issue, so the wire shapes a fake server cannot vouch for are exercised against the real API — it was **not run** in this change because no Forgejo token was available in the environment. Inbound webhooks (Gitea-style HMAC-SHA256) are a later binding on ADR 0029's seam; the point of a second webhook provider is that it needs no second ingress. Additive public API (`connector/forgejo`) — `Semver: minor`- ADR 0032 — exposing services over the navi p2p transport (accepted, NAVI-409): a single versioned **service protocol** (`/opennavi/service/1.0.0`) carries a call as an operation name plus arguments, with operations declared as data and reusing `tool.Def` (one schema, not two); a p2p service is consumed by an ordinary **connector** (the same tools, the p2p transport instead of HTTP), and the **provider SDK is standalone** (usable outside a navi). The caller presents its **principal** in a signed, timestamped request (the peer identity reused, with the peer clock agreement); **authorization is the service's own** (the SDK provides identity and transport security, not policy); request/response and **streaming/pubsub** are both supported. **Discovery is a federated rendezvous network** — services register (opt-in) at p2p navi-relays, anyone may host one and contribute — and it **informs but never widens capability**: the discovery tool lists services and explains how to add one, while adding a tool, connector, or service is a human act (a rebuild/redeploy or a config change). A navi may **learn** (memory) and **propose** (explain, or open a PR), but not **effect** a capability change. The **self-improvement barrier** is also recorded in `security.md`. Docs only — no code changes. — `Semver: patch`
- ADR 0031 — the navi peer network: libp2p, tiers, and the relay as a role (accepted, NAVI-409/NAVI-412): the peer transport is **libp2p** (identity = the navi's Ed25519 principal → PeerID; QUIC/TCP, Noise, yamux, `ConnectionGater`, `pnet`, circuit relay v2, DCUtR, rendezvous, pubsub); **discovery is opt-in and off by default**; the **relay is a role** (rendezvous + circuit relay + mailbox) hosted by a dedicated service **or** a navi, with the peer path direct-by-default and the relay as rendezvous/fallback; **tiers** keep floodsub's domain small (teams of leaf navis, relay navis bridging, no federation tier until evidence — Aptos is deprecating its middle tier); communication is **streams** (point-to-point) and **pubsub** (floodsub first, topics scoped `team/<id>/*` vs `fleet/*`) with **topic ACLs from the permission system** and `StrictSign`; delivery is **durable** via store-and-forward (the navi's datastore as outbox, the relay's mailbox holding E2E-encrypted messages for offline peers) with presence from the rendezvous TTL and a heartbeat topic; **portals ride the peer network** (libp2p browser transports — WebTransport first, WebSocket fallback) alongside a **direct binding** that needs no p2p; a navi is a **user in every service** (Huly user, GitHub machine user with App opt-in, its own Discord bot), its job being its **name and system prompt** beside its **tool set** and **permission groups** (not a config field); and **work claims are the board** (assign-to-self in Huly, p2p as a courtesy heads-up), with **Huly inbound** (NAVI-561) the pick-up path. The deployment shapes are in `docs/design/p2p-topology.md`. Docs only — no code changes. — `Semver: patch`
- ADR 0030 — the navi's ingress: a webhooks listener and a websockets listener (accepted, NAVI-409): the navi's ingress is **two listeners, one per trust model** — a **webhooks** listener for third-party provider events (untrusted, signature-authenticated, connector-owned routes behind one router, ADR 0029) and a **websockets** listener for principals and peers (verified principal, a long-lived bidirectional stream) — and they do not share a socket, so a webhook can never reach a portal or peer route and a portal credential can never satisfy a webhook. It adopts websockets for ADR 0019's one stream (decision 4's condition — a named consumer — is met: portals, real-time connectors, and peer navis), leaving SSE + POST a supported binding and the stream contract unchanged; it extends ADR 0023 decision 3's connector inbound transports with a websocket binding, distinguishing an **inbound** one (a service connects to the navi's listener) from an **outbound** one (the connector dials a service's gateway — Discord is the case — an inbound source like polling, not a listener); and it names the websockets listener as NAVI-412's **first** peer endpoint, with a **peer-to-peer** transport (IPFS-shaped, or at least a connection with allow/deny lists) an additive real-time shape — allow/deny is required either way — leaving peer delivery semantics (ACK, store-and-forward, presence, and the clock agreement timestamped signed requests need) to that record. Each listener is declared and exposed independently, and ADR 0024's relay routes to both. Docs only — no code changes. — `Semver: patch`
- ADR 0029 — the webhook inbound binding: connector-owned endpoints behind one navi router (accepted, NAVI-409): the design record resolving the **navi-side** half of ADR 0023 open question 4 (ADR 0024 decided the fleet fabric). Webhook endpoints are **connector-owned**: the connector declares its route and secret reference at composition and provides the handler that verifies and processes, and the navi's portal surface is not the webhook surface — a webhook is authenticated by a provider signature, never by `portal.Authenticator`, so the two trust models do not share a dispatcher (ADR 0014 decision 3: no generic payload and no generic provider dispatcher). The navi owns **one shared webhook listener with a router** rather than a listener per connector — it is one of the navi's two ingress listeners (the other is a websockets listener for portals, real-time connectors, and peer navi traffic), so one address, one certificate, and one choke point — which is where the navi records an **inbound-events log** as structured log lines (time, source, route/provider, delivery id, verification outcome, and outcome; the persisted, browsable type is a follow-up, NAVI-433), a record a connector cannot bypass; the router reaches the connector as a stdlib-typed handle through `connector.Deps`. The navi verifies the provider's signature over the raw body **before** parsing, even for relay-delivered traffic (the relay is a boundary, not an authority, ADR 0024) — **HMAC-SHA256** for GitHub/Forgejo and **Ed25519 over a timestamped payload** for Discord interactions, with the scheme and its material typed in the binding (a shared secret, or a public key, which is not secret and may be pinned); the HMAC secret is an **array** of ADR 0008 references resolved at the point of use and never in the cluster, verified against each so a rotation can overlap; idempotency is the event's **normalized identity** — shared with polling, so the two transports dedupe against each other — in the same persisted seen-set, with the deterministic thought id as a second backstop, marked only after a successful enqueue; the payload is a bounded **stimulus** that becomes a thought and never the assembler's configuration (ADR 0013); and acknowledgement is provider-correct (2xx accepted/duplicate/undeclared, 401 bad signature, 405 non-POST, 413 oversized, 429 rate-limited, 400 malformed, 5xx enqueue failure so the provider retries), and rate limiting is layered at both the navi and the relay so neither is the only defense. Webhook and polling are one connector with two transports, polling staying the reachability-free fallback. The websockets listener and the two-listener ingress are ADR 0030. Docs only — no code changes. — `Semver: patch`
- Huly connector: labels, relations, and descriptions (NAVI-418, ADR 0014/0020): the remaining egress tools. `huly_issue_label` adds or removes a label — Huly's tags model is a `tags:class:TagElement` definition in the workspace space plus a `tags:class:TagReference` attached to the issue's `labels` collection, and a title the workspace has never used creates the definition first (matched case-insensitively); `huly_issue_relation` adds or removes `blocks` / `is-blocked-by` / `relates-to`, which are not documents but entries pushed into an issue's `blockedBy`/`relations` array; and `huly_issue_description` (read) / `huly_issue_description_set` (write) read and write the issue's rich text through Huly's **collaborator** service (`COLLABORATOR_URL`, a separate RPC), where an issue's `description` is a reference to a ProseMirror document — `createContent` mints the reference on the first write and an update transaction sets it, `updateContent` replaces the document after, and the text round-trips as paragraphs rather than formatting. Two live wire shapes the fake server could not catch are fixed, and both affect already-merged tools: Huly's `find-all` uses the query as an **exclusion projection**, so the field a document was matched on is absent from the response — `findProject` lost the project identifier (create produced `-419`, not `NAVI-419`) and `findIssue` lost the issue id, so a comment or label attached to nothing — and the client now restores the scalar query fields; and Huly has **no `$set` operator** (`TxUpdateDoc` applies a plain field map), so `huly_issue_update` was refused live and now sends the plain map. A new opt-in live smoke test (`HULY_LIVE_SMOKE=1`, skipped by default) exercises create, comment, update, description, label, and relation end to end against the live workspace and removes what it creates. — `Semver: minor`
- ADR 0028 — row-level read-scoping — is accepted (implemented as NAVI-416, #383). — `Semver: patch`
- Row-level read-scoping (NAVI-416, ADR 0025 decision 3, ADR 0028): a type may declare a **`Scope`** — a closed, referential rule that a named field must equal the acting principal's reference — and the surface ANDs it with the caller's query (the scope wins a conflict, so a caller narrows but never widens) and enforces it on the way out, while the provider applies it **before paging** so a page stays full. A row the scope excludes is reported as **absent**, not refused, because whether an id exists is itself scoped information, and the scope applies to every principal — the navi's service principal included, with no root exemption (an author who wants the console to see all rows simply declares no scope; the built-in types declare none). `thought.origin` now carries the **effective** originator — the principal, or `navi:<name>` for system work — so a scope on `origin` matches the runtime's own machinery. This also makes `object.Query.Filter` real: it was declared but applied by no provider, so a scope would have been a silent no-op; every built-in provider now filters before paging. Additive; a type with no scope is unchanged. — `Semver: minor`
- Huly connector: create (NAVI-418, ADR 0014/0020): `huly_issue_create` creates an issue in a project, optionally as a sub-issue of another, and returns its identifier and id. It follows Huly's own three steps — bump the project's **sequence** (a `$inc` transaction, whose answer carries the new number), place the issue after the project's last one with a **LexoRank**, and create it as a document attached to `tracker:ids:NoParent` (top-level) or to its parent (sub-issue, carrying the parent chain). The rank step is the small piece of LexoRank the append case needs (`ceil(value) + 8`); the create path was smoke-tested against the live workspace end to end (create, read back, remove). Status defaults to the project's default status, and an unknown status or project is refused rather than defaulted. — `Semver: minor`
- Huly connector: update and search (NAVI-418, ADR 0014/0020): `huly_issue_update` changes an issue's status, assignee, or priority in a single `TxUpdateDoc` — the status is resolved from a display name, the assignee from a person name or id (an empty value clears the field), and Huly's priority scale is mapped (`urgent`=1 … `low`=4, a LOWER number being a HIGHER priority) — and `huly_issue_search` runs the workspace full-text search and returns the matching documents with their identifier, title, and class. Both are ordinary egress tools built with `connector.SendTool`. Still open under NAVI-418: **create** (a project-sequence bump plus a LexoRank), **labels** (the tags model), **relations**, and an issue's **rich-text description** (which lives on Huly's collaborator service, not the transactor). — `Semver: minor`
- The Huly connector (NAVI-408, ADR 0014/0020): `connector/huly` lets a navi read the tracker and act in it, natively over Huly's REST API — not through an MCP server — so each capability is an ordinary `tool.Tool` and the package stays contract-pure (ADR 0004). A connection is Huly's own three steps: read the instance's `config.json` for its accounts URL, authenticate against it (an account-token reference, or email and password references), and select the workspace, which answers with the transactor endpoint and a workspace-scoped token. Reads are `GET /api/v1/find-all/{workspace}`, writes are `POST /api/v1/tx/{workspace}` with a single transaction object, and the workspace session is established lazily and dropped on a refused token so a revoked or expired one recovers on the next call. Two egress tools ship, added explicitly with `connector.SendTool` like every egress tool: `huly_issue_list` (issues newest-first, filterable by status name or a raw Huly query, with status and assignee names resolved; read-only, so a read-only mode may still read the tracker) and `huly_issue_comment` (a comment on an issue addressed by identifier or id — a `chunter:class:ChatMessage` attached to the issue's `comments` collection, with the text rendered as the ProseMirror document Huly stores). Every credential is a reference (ADR 0008) and is never a tool argument. Additive; wiring the connector into a navi is NAVI-407, and inbound Huly events are a follow-up. — `Semver: minor`
- ADR 0027 — attribution: the interaction record and the trust ledger — is accepted (implemented as NAVI-400, #378). — `Semver: patch`
- Attribution: the interaction record and the trust ledger (NAVI-400, ADR 0021 decision 12, ADR 0027): "who did what" and "who was trusted" are two records, deliberately separate. The **interaction record** is the navi's own state — `origin` and `lineage` join the thought type as read-only fields, so a portal reads who caused a thought and the chain that scheduled it (paired with NAVI-404's lineage), and it persists with the thought. The **trust ledger** is operator-facing: an append-only, bounded ring of the trust decisions the navi makes — a credential it `authenticated` (which principal, when, by which scheme) and a credential it `refused` (with the claimed principal and the reason). It never holds a credential (no token, signature, or key material), and it is exposed as a read-only `trust_event` type, so reading it is a capability (`read:trust_event`) rather than a bespoke endpoint. The ledger does not invent grants it cannot witness: a grant or revocation happens outside the navi (a compiled declaration, an operator editing a trust store), so a future operator path would append `granted`/`revoked` naming the operator. ADR 0027 records the split. Additive: `thought` gains two read-only fields and a new built-in type. — `Semver: minor`
- ADR 0026 — the session policy a mode imposes — is accepted (implemented as NAVI-397, #375). — `Semver: patch`
- The mode chosen at enqueue is a session policy (NAVI-397, ADR 0022 decision 4, ADR 0026): a thought's mode now narrows what that thought's tool calls may do and can never widen it, because the engine requires every layer — the compiled ceiling, the principal's roles and groups, and the session — to permit. The session is derived from the mode as wildcard allows plus a deny-list: it denies every declared tool the mode's access cap, deny-list, or tool subset excludes, and `act:*` when the mode is capped at read-only. The **selectable set** is principal-scoped and checked at the door — a mode that permits a tool the originator may not call is refused loudly when the thought is enqueued rather than silently narrowed when it runs, while a more restrictive mode is always selectable. The choice rides `thought.Thought.Mode`, is carried by the gateway's control route and `navi enqueue --mode`, and is validated by the queue's assembler. ADR 0026 records the derivation. Additive: a thought with no mode narrows nothing. — `Semver: minor`
- ADR 0025 — principal-aware reads — is accepted (implemented as NAVI-398, #373). — `Semver: patch`
- Delegated authorization: the acting principal reaches every enforcement point (NAVI-404, ADR 0022 decisions 1–3, 5–6 and 9): the compiled policy was built in NAVI-399 and wired to nothing, deliberately. Now attachment, the object read, the object action, and the tool call all ask the same engine about the same principal, and `enqueue` is the fifth verb at the portal boundary. `portal.Actor` carries the **verified principal together with `portal.RequestInfo`** — the transport and input channel the binding declares, the source address, and the time — so a condition is evaluated against the facts the binding supplied rather than refusing through a path for the wrong reason; the navi maps an action and its facts onto a capability and a request context, and the vocabulary still never reaches a portal (decision 8). `thought.Thought` gains **`Origin`, `OriginInfo`, and `Lineage`**: the originator is recorded at the door and a follow-up inherits it — a thought with no origin that declares a dependency takes that dependency's principal, request facts, and lineage, so `thoughts_create` chains a plan without the tool knowing who it acts for — while a thought with neither is **system-originated** and acts as the navi's own service principal `navi:<name>`, which holds the compiled ceiling by construction so fail-closed never disables cron, the closing check, or recovery (ADR 0021 decision 10). The **tool path is authorized per call as the originator** (`bridge.Options.Authorize`), closing the confused-deputy path where a principal launders an action through the agent and making a revocation take effect on the next call rather than at thought creation. The **object surface authorizes reads (`read:<type>`, a detail as its own type) and actions (`act:<type>.<action>`) as its actor**; its default actor is the in-process console, and `portal.Scoper` lets a network binding re-scope it per connection, so the surface no longer acts as one declared principal for every connection — `navi.WithObjectAuthorizer` remains as an explicit dev/test override. A **refusal is loud**: the engine's reason travels back to the call site, so a refused `enqueue` (or tool call) cannot look like nothing happened. Origin, lineage, and the origin facts **persist** (sqlite migration 18–20, the `fs` frontmatter, and the shared conformance suite), so a thought that survives a restart stays attributed to the principal that caused it instead of falling back to the service principal. The reference navi authorizes through the compiled policy and declares the `connector:github` role granting `enqueue`. Breaking (pre-1.0): `portal.Authorizer`, `portal.Portal`, and `portal.Control` carry a `portal.Actor` instead of a bare `principal.Ref` — the third move of those signatures (NAVI-403, NAVI-402, NAVI-404) — `thought.Thought` gains three persisted fields, and `internal/bridge.Options` gains `Authorize`. Read-scoping and field sensitivity as principal-aware projection remain NAVI-398, and the mode-at-enqueue session policy remains NAVI-397. — `Semver: minor`
- Compiled authorization policy: the capability vocabulary, roles, groups, and evaluation (NAVI-399, ADR 0021 decisions 3–5 and 11): **capability is compiled, identity is resolved at runtime**, and this is the compiled half. A **capability** is a closed verb (`connect`, `read`, `act`, `call`, `enqueue`) over a **referential** target — a tool name, a type name, a field name, an action name — so `call:shell_exec`, `act:thought.pause`, `read:thought`, and `read:thought.assembled` all name things the navi already declares, and a `read:<type>` grant deliberately does **not** cover a field: a sensitive field needs its own grant, which is how read-scoping and field sensitivity compose rather than duplicate. A **role** is a trust policy (who may hold it) plus a permission policy (what holding it permits); a **group** is the permission side of a collection whose membership comes from the trust source — membership is trust-side, capabilities are permission-side (decisions 4 and 5), and NAVI-403's compiled membership list is gone rather than becoming a second, conflicting source of the same fact. **Conditions** are the same design moment as the vocabulary, not a later extension: ADR 0022 decision 6 puts "every condition must pass" *inside* evaluation, and ADR 0021 decision 9 makes network a condition on a request, never an identity. A grant carries `When(...)`, and the first vocabulary is `OnTransport`, `OnChannel`, `OnNetwork`, `Between`, and `OnClaim` — so `When(Enqueue(), OnTransport("lan"))` and a mesh peer's narrower condition tell two requests apart without inventing a principal that encodes transport. The **input channel** is deliberately separate from transport (an SSH session is a console over a network transport; a voice portal is a microphone in-process), which is what makes the console-versus-microphone distinction expressible in policy rather than only documented — and it is not authority: a microphone grant is exercisable by whoever is audible, and a channel or transport label must not be reused across paths or a scoped grant widens silently. Evaluation is **default deny, explicit deny wins, allow required**, intersected with the compiled ceiling and with a session policy, every condition passing; the role and group layers **union** (grants accumulate) while the ceiling and a session policy are **required narrowing layers**, so a bare layer can never widen a conditioned one — the meet is the mechanism, not a comparison to get right. The **ceiling is derived** from what the navi declares — every tool, and every exposed type with its fields and actions — so the referential rule is true by construction and a role or group naming something undeclared fails `Run` rather than being discovered per request. Roles and groups are declared on the navi (`n.Roles`, `n.Groups`) like tools and models, and a refusal always carries a reason so an enforcement point can report it loudly instead of it looking like nothing happened. Breaking (pre-1.0): `navi.Role` gains its two policies and `navi.Group` loses `Members`/`Add`/`Remove`. Enforcement — carrying an acting principal and the request facts to the four enforcement points — is NAVI-404. — `Semver: minor`
- Portal connect: a verified principal replaces the asserted identity (NAVI-402, ADR 0022 decision 8, ADR 0021 decisions 6–8): the client-asserted `identity` query parameter, the `X-Portal-Identity` header, and the control body's `identity` field are **gone**. A portal now presents a credential — `Authorization: Bearer <oidc-token>` for a human, or a `Navi-Ed25519` signed request for a service or peer navi — and the navi resolves it through its declared trust sources, answering with a verified principal reference or a refusal. The gateway never decides whether a credential is valid and never evaluates policy: `portal.Authenticator` is the seam, handed to every portal through `portal.Deps`, and a gateway with none authenticates **nobody** (HTTP 401, fail closed). A signed request binds the method, the path, a digest of the body, and a timestamp, so a captured signature cannot be replayed with different content or outside a short window; the transport checks the timestamp against its own clock, never the wire's, and a refusal is logged rather than returned as an oracle. `portal.Portal`, `portal.Control`, and `portal.Authorizer` are asked about a `principal.Ref` rather than a string, so every attach and control action is authorized for a principal the navi verified, and `navi.WithObjectAuthorizer` takes a principal reference too. The in-process console is unchanged and structural — it is the binary the operator is sitting at, with no transport, so it presents no credential and does not come through the seam at all (a statement about its **input channel**, not about being in-process: a portal whose input is a room microphone must authenticate as a real principal) — while `portal.AllowAllAuthenticator` is the explicit **development default** the reference navi wires only behind `--dev-allow-all`. `navi connect` gains `--token`, and `--principal`/`--key`/`--key-id` for a signed request; `navi host` gains `--trust-store`, `--oidc-issuer`, and `--oidc-audience`. Breaking (pre-1.0): the `portal.Portal` and `portal.Authorizer` signatures and `gateway.Handler` change, and an unauthenticated remote portal is now refused — a navi serving a gateway must declare a trust source or opt into the development default. — `Semver: minor`
- Trust sources: inline, an OIDC identity provider, and a keyed trust store (NAVI-401, ADR 0021 decisions 4, 6–8): identity is now resolved at runtime from sources a navi declares at build time, exactly as a credential reference is (ADR 0008). `navi.TrustSources` is one ordered, compiled set — `navi.Principals` (inline, the break-glass), `navi.OIDC` (an identity provider), `navi.FileTrustStore` (a keyed store) — and resolution walks it in declaration order, so a source that cannot answer never masks one that knows the reference: an unreachable IdP leaves the compiled principals resolving, and a reference nothing knows is refused rather than defaulted open. `navi.OIDC` verifies a bearer token against the provider's published keys with the standard library alone (RS256 and ES256, `kid` selection with one refetch on a miss, discovery or an explicit JWKS URL, cached key set) and enforces `iss`, `aud`, `exp`, and `nbf` with a small clock skew; `alg: none` and HMAC algorithms are refused by name so a public key can never double as a signing secret. The provider supplies **identity and claims only** — never policy (ADR 0021 decision 7). `navi.FileTrustStore` resolves principals, their Ed25519 keys, their claims, and their group membership from a document whose path is an ADR 0008 reference (an environment variable name or a path), re-read on a bounded TTL so a **revocation or expiry narrows what verifies at runtime** (decision 8) — revoked and expired keys are dropped, not trusted. `navi.Principal` gains the identity data a trust source supplies (`Claims`, `Groups`, `InGroup`, via `NewResolvedPrincipal`), kept separate from policy. A navi declares sources with `navi.WithTrustSource` and exposes the compiled set as `navi.Navi.Trust`; declaring none leaves an empty, fail-closed set rather than a default. Additive public API — `Semver: minor`
- The principal model: identity, authenticators, and a validated memory subject (NAVI-403, ADR 0021 decisions 1–4): a principal is an identity with **authenticators attached**, and kinds are open (`user`, `service`, `connector`, `navi`, `group`, and future kinds), so the model does not need a contract change to grow. A principal holds a **set** of keys, so rotation and revocation never change identity and the key system is pluggable. The new stdlib-only `principal` contract package carries the one thing that crosses a contract boundary — `principal.Ref`, a validated `kind:name` reference that cannot be built invalid — while the model itself stays core navi: `navi.Principal` attaches and detaches keys by id, `navi.Authenticator` is the seam an OIDC session (decision 8) attaches through without reshaping the principal, `navi.Ed25519Key` is the first implementation for services and peer navis (with an optional validity period; key material is generated in tests, never a literal, ADR 0008), `navi.Group` is a collection of principals that may be authenticatable itself as a shared identity, and `navi.Role` is a compiled capability set and deliberately not a principal. `navi.TrustSource`/`navi.Principals` are the compiled, fail-closed seam the concrete trust sources of NAVI-401 resolve through: resolution returns an identity and never a capability, and an unknown or zero reference is refused. `memory.subject` is a principal reference rather than a free string — `datastore.MemoryRecord.Subject` and `RecallQuery.Subject` are `principal.Ref`, the runtime keys short-term memory by the navi's own service principal `navi:<name>` (decision 10), and the GitHub connector's `Subscription.Principal` — the first consumer — is one too. **Migration**: the runtime previously wrote the navi's bare name, so `principal.ParseLegacy` reads an unqualified stored value as `navi:<name>` and the persisting backends apply it on read (`fs` normalizes the frontmatter subject; `sqlite` normalizes on scan and matches the bare legacy form in its subject filter), keeping pre-change rows visible until they are rewritten. A thought's transcript is keyed by thought id and written as a unit; `TranscriptInfo` answers from a metadata projection (`thought_transcript_meta`) so enumerating thoughts or transcript metadata selects **no message body** — the property the shared conformance suite proves through `conformance.ReadReporter`, which the backend now implements. The backend is configured for the datastore's one ordered writer: WAL plus a busy timeout, so a flush never blocks a read and a second process sharing the file waits rather than fails. Transcript message bodies and tool input are encrypted when `NAVI_SESSION_KEY` is set (the cipher seam is kept and now actually wired); memory and notes stay plaintext because recall and note search match them with literal substrings. Migrations are append-only: an existing `navi.db` is upgraded in place — thought rows survive and the retired `sessions`/`messages` tables are left untouched — never half-read. New `templates/navi-sqlite` shows a navi whose whole state lives in one file. The backend runs the shared conformance suite in CI, and its own tests cover candidate selection, WAL, body-free metadata reads, transcript encryption, an empty transcript, and reopen-without-loss
- The `fs` datastore backend (NAVI-365): the navi's state as a directory tree a person can read, diff, and back up with ordinary tools — and the step that ends the volatility. `fs` is now the **compiled default** (ADR 0011), so the reference navi's transcripts, tool state, and memory survive a restart; `inmem` stays declared as the non-durable reference, selectable with `datastore.backend: inmem`. Layout under one per-navi root (`datastore.params.path`, required — the backend fails loudly rather than guessing a location): `thoughts/<thoughtID>/thought.md` (frontmatter is the thought row, including `depends_on`, skills, the assembled context, a base64 checkpoint, and the transcript's message count and update time; the **body is the transcript**, rendered as a readable conversation with one marker comment per entry), `todos/<naviID>/manifest.md` + `todos/<naviID>/<todoID>.md` (the manifest is the batch's atomic anchor, written last, so a rejected or interrupted batch leaves the previous list authoritative), `notes/<naviID>/<noteID>.md`, and `memory/<scope>/<id>.md`. Two properties are structural: **metadata without bodies** — enumeration reads frontmatter only (the reader stops at the closing delimiter, and `TranscriptInfo` answers from stored metadata), which the conformance suite checks because this backend implements `conformance.ReadReporter`; and **atomicity** — every write is temp-file + rename, so a reader never sees a half-written file and a failed write leaves the previous one in place. `Open` takes an advisory lock on `<root>/.lock`, so two processes on one root fail loudly instead of silently interleaving. The backend runs the shared conformance suite in CI, and its own tests cover readability, enumeration-without-bodies, restart read-back, root exclusivity, manifest anchoring, and failed-write atomicity. `cmd/navi` declares both candidates and roots `fs` at `<db-dir>/state` (`var/data/state`), which a `datastore.params.path` in runtime config overrides; `inmem.Candidate()` is no longer marked default (exactly one candidate may be). Bounded/cursor transcript reads are deliberately not here — the contract has no paged read (see NAVI-376's scoping note)
- Backend conformance suite (NAVI-376): the datastore contract now ships its own **shared conformance suite** (`datastore/conformance`), so a backend is provable rather than plausible. One entry point (`conformance.Run(t, open)`) plus per-aggregate entry points assert the behaviour a consumer depends on: thought round-trip across every durable field (including `DependsOn`, `Skills`, `Assembled`, checkpoint and metadata), transcripts written as a unit with entry order and tool-call fields preserved and `TranscriptInfo` agreeing with the body, tool state (todo replace and all-or-nothing update batches, notes verbatim, **per-navi scoping**), memory (recall filters, most-relevant-first ordering, expiry **carried not interpreted**), documented failures returning wrapped sentinels rather than silent success, caller memory never aliased, and concurrent readers never blocked or failed by an in-flight write. The suite belongs to the contract, not to the in-repo backends: `internal/testdata/external-backend` is a synthetic out-of-repo backend module that imports and runs it in CI, and the `external-consumer` guard now checks that fixture's boundary — including its **test-only** imports, where the suite is imported — exactly as it checks a third-party author's. "Metadata without bodies" is *proven* rather than asserted: an optional `conformance.ReadReporter` lets a backend report transcript body reads, the reference backend implements it, and a backend that does not is reported as **unverified** instead of passing silently. `datastore/inmem`'s aggregate round-trips moved into the suite, leaving only what is specific to the in-memory backend. Two items the issue named are deliberately **not** invented here because the contract has no such surface: a cursor/limit transcript read (the suite asserts the metadata/body split that exists, and a cursor read belongs to NAVI-361/364) and a capability-reporting API for prunable things (sentinels and assembly-time validation are what exist today, and NAVI-363 is where the capability surface lands) — both recorded as open questions on the issue. `runtime.md`, `overview.md`, and `memory.md` reconciled
- Plan closing checks (NAVI-379, ADR 0016): a plan of thoughts is no longer done when its last stage completes. `core_thoughts` now tells the model to close a multi-stage plan with a **verification thought** — `depends_on` set to the stage it checks, metadata `role: verification` — carrying a concrete check of the result (run it, read it back, diff it) rather than another implementation step. The **runtime guarantees it**: when a plan drains with no check behind it, the navi queues one itself (`navi.WithPlanCloseCheck`, on by default). The rule is mechanical rather than heuristic: the plan is the dependency-connected component of the completed thought (NAVI-378's graph — no plan object), every member must be `complete` (a failed or cancelled stage means the plan did not succeed, and its dependents were already failed), a plan containing a verification is left alone so a check never spawns another, and the synthesized check depends on the plan's **sinks** — so parallel branches are covered — with an id derived from those sinks so a replayed event or a restart cannot queue a duplicate. A standalone thought is not a plan and is not closed. New public graph helpers `thought.Plan`/`thought.PlanSinks`/`thought.PlanSucceeded`, the `thought.RoleVerification`/`MetadataRole` vocabulary with `Thought.IsVerification`, a `V` flag on the TUI row, and `thoughts_create` guidance for the model's own closing check. ADR 0016 is the design record and `runtime.md` gains a *Closing a plan* section
- Thought dependencies (NAVI-378): a plan of thoughts can now keep its order. `thought.Thought` gains `DependsOn []string` — the ids this thought waits on — persisted with the row (`depends_on`, migration 15) and copied by `Clone`. `Queue.Dequeue` refuses to claim a pending thought until every dependency has reached `complete`, so a later stage cannot start before its predecessor **with more than one worker and with preemption in play** (a paused dependency is not complete — preempting a chain's head parks the chain). There is **no new lifecycle status**: "blocked" is derived for display (`thought.UnmetDependencies`, surfaced as `blocked_by` on the thought tool view and `blocked` in the TUI row), so the scheduler and the record keep one vocabulary. A dependency that fails, is cancelled, or is removed fails its pending dependents transitively with a detail naming the dependency (`pending → failed` joins the transition matrix, so a dependent is retryable; `Retry` re-applies the gate), and a graph loaded with an already-dead dependency settles the same way at recovery and external adoption. `Enqueue` validates at the door — every id must already exist, self-dependency is rejected, and an edge that would close a cycle is refused — which together with unique ids makes an in-process graph acyclic by construction. `thoughts_create` takes `depends_on` and returns the created id, so the model chains a plan by naming the ids it just created ("this continues `t1`"). ADR 0015 is the design record and `runtime.md` gains a thought-dependencies section. Additive state-machine and ABI change — `Semver: minor`
- Thought context assembly (NAVI-368): context is now assembled **at thought creation** and carried by the thought. `thought.Queue.SetAssembler` is the seam — the composition root installs its assembler on the queue it owns, so every enqueue path assembles once, at the door, and a thought that cannot be assembled (an unknown declared skill) is rejected at `Enqueue` rather than mid-run. The assembled block (personality, mode fragment, loaded skills, short-term memory) is persisted on the row (`Thought.Assembled`, migration 13; declared `Skills` alongside it, migration 14), the runner consumes it instead of rebuilding per turn, and it is recorded as the thought's **first transcript entry** (index 0) so it is readable through the same contract as the rest of the transcript. Assembly is build-time-only and reproducible, and it truncates past the navi's budget with a reported marker (`WithThoughtBudget`, default 16k). The **deferral trigger** ships: as a run approaches its budget the agent loop injects one notice telling it to finish a coherent unit, write the handoff with `memory_write`, and queue follow-ups with `thoughts_create` declaring their skills. A successor inherits only what short-term memory carries
- Core skills (NAVI-372): `n.Skills` is now read. The runtime generates a core skill for each component type the navi actually declares — authored prose for semantics (`skill.CoreTools()`, `CoreThoughts()`, `CoreConnectors()`, …) — plus a mechanical `core_inventory` derived from component metadata, so the model is never unaware of a capability the binary has. All three loading paths of ADR 0013 decision 5 now exist and resolve against the compiled-in set only: author-declared auto-load (`skill.Skill.AutoLoad`), a thought's declared request (`thought.Thought.Skills`, settable through `thoughts_create`), and the agent-chosen `skill_load` tool (`n.SkillTool()`, added explicitly like any other tool). A request for an unknown skill fails the thought rather than fetching anything, and `core_` is a reserved namespace. The auto-loaded core set is bounded by the declared component types and measured (~300 tokens for a 7-tool navi, pinned by `TestInventoryTokenCost`); `cmd/navi` adds the skill tool
- Short-term memory (NAVI-351): the always-loaded tier of the memory model (ADR 0013) ships as a navi-internal service (`internal/memory`) — `user` and `session` notes held in RAM, hydrated once at assembly from the datastore's memory view, injected into **every** thought's system prompt so no tool call is needed, and written back through the ordered writer. `navi.WithShortTermMemory()` declares it, and the runtime registers the built-in `memory_write` tool (add/replace/remove, `user` or `session` scope) as the deliberate write surface — kept navi-internal rather than published as a `tool/memory` component package, so an out-of-repo module cannot reach it. A note written during thought *N* is visible to thought *N+1* immediately (it lands in RAM, not only on flush). Declaring memory with no datastore candidate fails at `Run` with a clear error rather than silently keeping memory volatile. The `navi` and `memories` scopes stay with long-term memory (NAVI-350); metadata-first hydration and retention are deferred (NAVI-377/NAVI-363). `cmd/navi` enables it
- Context assembly and connector scope (ADR 0013, ADR 0014): the **thought queue is the context mechanism**. Context pressure is resolved by bounding thoughts and deferring work into follow-up thoughts — a thought approaching its budget finishes a coherent unit, writes what the next one needs into short-term memory, and queues follow-ups declaring which skills to load — rather than by compacting a long conversation, which is why **compaction is being removed** instead of kept as a fallback. Context is assembled **at thought creation**, not per turn, and the assembled context is recorded as the thought's first transcript entry so it is readable through the same contract as the rest of the transcript. Everything that shapes context is a **build-time declaration** — sources, auto-loaded skills, component-derived guidance — because if a prompt can reach the assembler then the assembler is an injection surface; runtime config may only narrow it. **Skills are loaded selectively** through three paths (author-declared auto-load, thought-declared request recorded when the thought is queued, agent-chosen tool), all restricted to the compiled-in set, so a manipulated request can at worst load a skill the author already shipped. Core skills ship with the component types: authored prose for semantics plus a mechanical inventory derived from component metadata, so the model is never unaware of a capability the binary has. Separately, **connectors are redefined as bidirectional service integrations**, amending ADR 0010's "inbound only" wording: inbound they turn external stimuli into thoughts, outbound they supply the tools that act on that service via `connector.SendTool()`, added explicitly and never auto-registered. Egress payloads are service-specific, so there is **no generic webhook schema**, and role separation between navis is **structural** — a function of which components and tools exist in a binary, not of what a prompt says. `runtime.md` (new context-assembly section, rewritten connector bullet), `security.md` (new *Context and the injection boundary* and *Egress* sections), `memory.md` (short-term memory as the inter-thought carrier, now on the critical path), and `overview.md` reconciled. Docs only — no code changes; the compaction removal is tracked separately. Delivery: NAVI-368 (context assembly) and the connector/egress issues under epic NAVI-362
- Persistence and portal-stream design (ADR 0011, ADR 0012): persistence becomes a selectable `datastore` **component** and RAM is the source of truth at runtime. The store leaves the read path — metadata loads eagerly at cold start while transcript detail loads on access and is garbage-collectable, transcript writes are asynchronous per message, and one globally ordered writer batches on flush so a crash leaves a *prefix* of history rather than a per-aggregate patchwork. Consumers depend on **per-aggregate views** (thought/transcript, tool state, memory) and the collection routes aggregate → active backend, defaulting every aggregate to the single active datastore — so multi-backend is a config change rather than an ABI change. `store` is renamed to `datastore` and its session-CRUD interface is **deleted rather than carried forward**; tools and memory are datastore consumers, and both memory tiers require a configured datastore; retention defaults to unbounded behind an explicit prune mechanism. ADR 0012 (proposed) replaces the separate observation and control surfaces with **one bidirectional navi stream** a portal translates for its transport, opened with a bounded state snapshot, with read vs write decided by IAM scope per portal. `runtime.md`, `overview.md`, `memory.md`, and `extension-model.md` reconciled. ADR 0010 stands: a datastore sits *beneath* the thought system and is a new component kind, not a fourth capability layer. Docs only — no code changes. Delivery is tracked under epic NAVI-362: NAVI-360 (datastore component + integration surface, including the shared backend conformance suite), NAVI-365/NAVI-364/NAVI-367 (`fs`/`sqlite`/`postgresql` backends), NAVI-366 (per-aggregate routing), NAVI-363 (explicit prune), and NAVI-361 (portal consumption), with NAVI-353 reduced to the design record
- M6 — synthetic out-of-repo CI modules (NAVI-346): `tools/external-component` is its own module publishing a tool, a connector, and a fail-closed portal that import **only** the public contract packages (`tool`, `thought`, `connector`, `portal`, `model`, `skill`), and `tools/external-navi` is its own module composing the public `navi` root over that component and validating it. The CI guardrail builds and runs both and asserts the component's import boundary — its direct imports must be public contract packages, and its dependency closure must not reach `navi` or `internal/` — so an extension author outside this repository provably needs nothing but the public surface
- M5 — the reference navi and the starter templates (NAVI-347). `cmd/navi run` now assembles through `navi.New` instead of `internal/daemon.Assemble`: the reference navi builds durable stores, the full catalog, configured providers (with the ADR 0009 fallback chain and `--compact-budget` compaction), the cron connector, and its portals, then calls `navi.Run`. `enqueue`/`health` are unchanged; daemon mode additionally serves the HTTP portal gateway, and the gateway is now a real control surface — the public `portal.Control` + `portal.Authorizer` let remote front-ends attach, observe, and control (queue, steer, pause/resume/cancel, bump, retry) across processes. `portal/tui` is public and `internal/portal/cli` (the legacy REPL) is deleted: the default command runs the navi (TUI, or headless with `--daemon`). `navi-code` and `navi-daemon` are converted to real `navi.New` modules (no `sdk.Build`). ### Fixed
- The Huly connector's transactions carried the wrong author (NAVI-418): `huly_issue_comment` and `huly_issue_update` set a transaction's `modifiedBy`/`createdBy` to the **account uuid** `selectWorkspace` reports, which Huly refuses with `AccountMismatch` — its own client builds its transaction factory from the account's **primary social id**. The connector now reads `GET /api/v1/account/{workspace}` and uses `primarySocialId`, so comment, update, and create all work against the live server. Caught by smoke-testing the create path against the live workspace; the fake-server tests now pin the author. — `Semver: patch`
- `TestReconcileAdoptsExternalPending` is deterministic (NAVI-417): the reconcile loop collects an adopted thought and its `EventEnqueued` under the queue lock but emits the event **after** releasing it, and the test waited for the thought to appear in `GetThoughts()` and then read the recorded events — so it could observe the thought before the emit landed and fail with `no external-adopted enqueue event: []` (seen twice on docs-only PRs). The test now waits for the in-memory adoption and its event in one predicate, which is correct regardless of the emit's timing. Test-only; no production code changed. — `Semver: patch`
- OIDC-authenticated principals were refused at authorization (NAVI-415, regression from NAVI-404): `portal.Authenticator.Authenticate` returns only a `principal.Ref`, and the navi re-resolved that reference at authorization time — but an OIDC principal is derived from a **token**, not looked up (`OIDC.Resolve` refuses a reference), so with OIDC as the only declared trust source every authenticated connection was denied, and with a trust store also declared the token's claims and groups were discarded in favour of the store's (so `OnClaim` conditions and claim- or group-gated roles never matched). `navi.TrustSources` now **remembers the principal a credential resolved** for a short, bounded window (`ResolvedCacheTTL`, 30s) and answers `Resolve` from it; only `VerifyToken` populates the cache, so a reference resolved from a store stays uncached and a revocation there takes effect at once, while a remembered principal outlives a revocation by at most the TTL. Fail-closed throughout — an unknown or stale reference still refuses. — `Semver: patch`
- The deferral tests are deterministic (found in NAVI-402 CI): `TestDeferralSurvivesRestartViaSqlite` (`datastore/sqlite`) and `TestQueueDefersUntilDue` / `TestQueueDeferralSurvivesRestart` (`thought`) asserted a not-before property against a **400 ms** window and then slept 600 ms. A loaded CI runner under `-race` can exceed 400 ms between the enqueue and the dequeue — the sqlite one does a store close, a reopen, and three database opens in that window — so it failed intermittently with "deferred thought claimable right after restart" on a PR that did not touch the file (a rerun passed). Each now uses a **far-future** deferral for the "not claimable" half and an **already-past** one for the "claimable once due" half, so neither half waits on a wall clock. Test-only; no production code changed — `Semver: patch`
- A portal that stopped draining was blind to work queued elsewhere (NAVI-389): two symptoms, one cause — `navi connect` showed "(no object types exposed)" indefinitely, and a thought queued *from* the remote client never appeared on the host. NAVI-335's idle-free tick ended the observation drain on an empty read ("no busy-loop"), which assumed the TUI was the only actor; but a navi changes from outside it (`navi enqueue`, cron, another portal, the remote client), and a remote client made it worse by racing that first idle tick against its asynchronous descriptor fetch. The drain is now **never stopped**: an idle read re-arms at a slower cadence (1s, which still ticks the age column) while the active 150 ms cadence applies whenever something is running, whenever the watched navi is in another process (a new `Transport.Remote()` states that rather than implying it), and while the descriptors have not arrived. The empty view also stopped lying — it says it is waiting for the navi's types, and an unreachable portal reports the transport error in the status line (the gateway client records why `RefreshTypes` failed) instead of showing nothing. Regression tests: an idle portal keeps draining and re-reads when an external enqueue arrives, and a client attached to a real served gateway renders the host's queue — both fail against the old condition (verified). The push stream (NAVI-390, ADR 0019) later replaced this cadence entirely: the portal is woken by the mailbox instead of a timer, so the blindness this fix worked around is gone by construction
- The gateway panicked on a fast shutdown (found while validating NAVI-389): `Gateway.Start` launched a serve goroutine that read `g.srv`, which `Stop` sets to nil — so a shutdown racing the goroutine's first read dereferenced a nil `*http.Server` and crashed the process (reproduced with `navi host --daemon` and stdin already at EOF, where the session drains immediately and the run tears down at once). The goroutine now keeps its own reference to the server it serves; `navi host --daemon < /dev/null` starts and exits cleanly
- The closing check could fire on a partial plan (NAVI-382): a navi stages a plan one stage at a time — `thoughts_create` returns the id the next stage names — so between two calls the queue can be momentarily *drained* (every thought complete, the next stage not yet enqueued) and the runtime closed the partial plan. Two consequences, both real: a **premature check** verified a stage the plan no longer ended at — exactly the "a check that does not check the real result" failure ADR 0016 exists to prevent — and because synthesis skipped any plan that already contained a verification, the **extended plan never got a proper check** (the same hole covered a plan deliberately extended after it drained). The skip condition is now "the plan's sink set is not already closed" rather than "the plan contains no verification": a verification is a check, not a stage, so it no longer counts toward the plan's shape (success and sinks are read from the stages alone), and a plan is already checked only when a verification depends on **exactly the current sinks**. When the plan grows past an earlier check, its successor is queued — and the superseded check, if it has not started, is cancelled first (`Queue.Cancel`; a check the model queued itself is left alone, and a check that already ran is kept). A verification is never re-closed (no check of a check), a standalone thought is still not a plan, and the synthesized id still derives from the sinks, so a replayed event or a restart cannot queue a duplicate. Tests: the incremental case is staged with **no gate on the plan's stages** — stage 1 completes before stage 2 is enqueued — and pins both the final-sink check and the cancellation of the superseded pending one; a plan extended after it drained gets a fresh check while the completed superseded one is kept
- The queue's event fanout now meets its own contract (NAVI-67): `emit` documents that it MUST run without `q.mu` held, because an observer may re-enter the queue — but `PauseWithCheckpoint`, `Resume`, `Complete`, and `Retry` still dispatched handlers while holding the lock, so any observer that read a thought from one of those events (`GetThought`/`GetThoughts`) deadlocked the queue. Reproduced with a re-entrant observer on `EventCompleted` (`Complete` → `emit` → `GetThoughts` blocking on the mutex `Complete` still held). All four now follow the collect-under-lock / emit-after-unlock pattern the rest of the queue uses (`Fail` and `Cancel` were converted in NAVI-378), so the documented guarantee is true again. The regression test drives every emitting transition — enqueue, dequeue, complete, pause, resume, fail, retry, cancel, delete — with an observer that re-enters the queue, each on its own queue, and names the transition if one deadlocks. Beyond event timing (an event now fires after the lock is released rather than while it is held) there is no behaviour change
- The live chat view still duplicated its events (NAVI-381): NAVI-380 fixed the cursor *write*, but every `Update` path re-armed the feed drain, so a key press (or `WindowSizeMsg`) stacked a second `tea.Every` timer while the previous one was still in flight. The mailbox read is non-destructive (a bounded replay ring), so N stacked timers each read the same range and each applied it, and a stale timer's captured cursor let the model's cursor move *backwards*; the chat showed each event once per in-flight timer — `ALPHA`, the run's system lines, `ALPHA` again, and so on. The drain is now single-flight (`tuiModel.polling`; re-arming while one is armed is a no-op), the idle-stop decision moved into `Update` (the poll command always returns a possibly-empty `feedMsg`, and `Update` stops the drain only when the mailbox was genuinely empty and nothing is running, preserving the NAVI-335 idle-free tick without a command goroutine touching the model; `tickMsg` is removed), and `Update` applies only events past the consumer cursor and never moves it backwards, so a duplicate delivery of an applied batch is ignored rather than re-appended. Regression tests: a duplicated batch no longer re-appends its turns (fails against the unfixed code), re-arming while a drain is in flight is a no-op, and an idle read still stops the drain
- The live chat view (NAVI-380): streaming deltas were duplicated (`NowNowNowNow…`) because the TUI advanced its feed cursor inside a `tea.Cmd` goroutine — a write that races and can be lost, so already-applied events were re-read and re-appended. The cursor now advances in `Update`, carried on the batch. Content deltas also lost their inter-token spacing (`I'llrun`) because `agentDetail` trimmed every fragment; a delta is now preserved verbatim and only whole messages are trimmed. ### Changed
- Principal-aware reads: field sensitivity is a grant, not static omission (NAVI-398, ADR 0022 decision 7, ADR 0025): the object surface no longer drops every `Sensitive` field for everyone. A sensitive field is now one a principal may see only with the grant `read:<type>.<field>` — which a `read:<type>` grant deliberately does not cover, so the read gate decides whether the type is readable and the field grant decides which fields. Projection is principal-aware on every read path (`List`/`Get`/`Detail`, a detail projected against its own type), a field the principal may not read is **absent, never null**, and the descriptor's `Sensitive` flag remains the declaration that a grant is required (resolving ADR 0017 decision 5's allow-list). A **delta never carries a sensitive field**, because the live window is shared by every connection; a granted principal reads the field through `Get`/`List`/`Detail` (ADR 0025 decision 4). The in-process console and the reference navi are unchanged in effect — the service principal holds the compiled ceiling, which includes every field grant — while a remote principal holding only `read:<type>` now sees the type without its sensitive fields.
